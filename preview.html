Booking Service — Production Saga Architecture

Mental model for the modular structure: HTTP/API → Booking domain → transactional Outbox → RabbitMQ → other Saga participants, with persistence isolated behind repository interfaces.

1. High-level architecture

HTTP / API internal/http/handler.go

Receives requests and delegates to the application/domain service.
→
Booking Service internal/booking/

Owns Booking and its business operation.
→
SQLite internal/repository/sqlite/

Persists Booking + Outbox in one local transaction.

Saga / Events internal/saga/

Defines messages that represent state transitions and compensation signals.
→
Transactional Outbox internal/outbox/

Stores the event atomically with the Booking transaction, then publishes asynchronously.
→
RabbitMQ internal/messaging/

Transport layer. The Outbox publisher sends events here.

2. Booking creation — the important production flow

1. POST /bookHTTP handler receives BookingRequest
→
2. Create BookingDomain/service creates RESERVED booking
→
3. DB TransactionSave Booking + Outbox Event
→
4. CommitBoth records become durable together

5. PublisherBackground worker finds PENDING events
→
6. RabbitMQPublishes BookingCreatedEvent
→
7. Saga continuesPayment / other services react
Key idea: the HTTP request does not need RabbitMQ to be available in order to durably record the booking and the intention to publish an event. If RabbitMQ is temporarily unavailable, the Outbox event remains PENDING and can be retried.

4. Who depends on whom?

HTTP → Booking Handler knows the Booking service/use case. HTTP should not know SQLite or RabbitMQ details.
Booking → Repository Booking defines the persistence contract. SQLite implements that contract.
Booking → Outbox The booking transaction creates an Outbox event as part of the same DB transaction.
Outbox → Messaging Publisher depends on a messaging interface, not directly on RabbitMQ behavior.
Messaging → RabbitMQ RabbitMQ is an infrastructure/transport implementation.
Saga → Events Saga defines the business workflow and the events used to communicate state changes.

5. The Saga mental model

Booking Service Reserve booking
↓
BookingCreated
→
Payment Service Process payment
↓
PaymentSucceeded / PaymentFailed

Success path Booking → Payment → Confirmation
↔
Compensation path PaymentFailed → compensate Booking → CANCELLED

The important distinction is that this is not one distributed database transaction. Each service owns its local transaction. The Saga coordinates the overall business process through events and compensating actions.

6. Production concerns to add as we evolve

IdempotencyConsumers must safely process the same event more than once.
RetriesTransient messaging/database failures need controlled retry behavior.
Dead-letteringPoison messages should eventually be isolated for investigation.
Correlation IDsTrace one booking across HTTP, services, events and compensation.
Outbox lockingMultiple publisher instances need safe claiming/processing semantics.
State machineExplicit Saga/Booking states prevent invalid transitions.
